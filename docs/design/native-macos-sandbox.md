# Native macOS workspace sandbox — #172 NMAC1.0

This is an opt-in Product slice for the current source/next built package. The public v0.1.9 release is unchanged and does not contain this option. Independent review and the concrete high-risk Human gate remain required; this design is not a project-fact register.

```sh
pan-agent --native-sandbox --workspace /absolute/project --memory-root /absolute/disjoint/archives
```

Use a normal interactive terminal with Node 22.19.0+ on macOS, `/usr/bin/sandbox-exec` and `/usr/bin/otool`. The installed package has compiled JavaScript; it needs no source checkout/compiler, Docker, Python, new npm dependency or service. The option applies to the ordinary interactive CLI only. `loop`/`goal`/`execution` retain their existing interfaces and do not accept this native flag. Current trusted-local default and Docker `--sandbox-root` remain available; Docker/native flags cannot be combined. No host fallback is implemented in this slice.

## Boundary and composition

`NativeMacSandbox` owns one policy and private temporary directory per admitted task, using the existing Session execution-boundary lifecycle. The existing trusted-local file implementation remains host-mediated, guarded by a workspace/protected policy before authorization and at effects, and by existing `AuthorizedFile` no-follow/handle checks. Shell uses the same live workspace through macOS Seatbelt. Files edited through `read/write/edit` are immediately visible to Shell and ordinary controlled descendants. No copied workspace or return-copy workflow exists. The native composition registers only these four tools; retrieval is absent.

Existing Session permissions.deny runs before tool dispatch and approval; approval/trust cannot expand the fixed OS profile or override native file restrictions. Normal Shell approval is still used in this initial slice. The TUI labels native offline execution, and each run archives an `execution.boundary` record and Shell results with policy identity. `policy.sb` and `identity.json` remain outside the project under `MEMORY_ROOT/native-sandbox/RUN_ID/`; only that run's `temporary` subtree is writable by the task. Temporary data is removed after normal settlement; these control records and the sealed Run Archive remain for diagnosis. Existing local Runbook/attachment selection is user-mediated and does not grant a model tool broader resources.

## Actual policy

The profile starts with deny-default. Executable launch is restricted to those same declared system/runtime/workspace/temp authorities, with protected paths explicitly denied for execution as well as read/write. Shell and descendants may read/write the selected workspace and task-owned temporary directory, subject to protected-path denies. No whole user HOME, `/Users`, `/private`, `/usr/local`, or whole `/opt/homebrew` read root is granted. No network or Mach service access is granted: direct TCP, UDP, local/private services and Unix sockets are unavailable in this slice. Public networking and explicit service grants are follow-on #174; scoped file/credential grants are #175 and host/full-auto exceptions are #176.

Fixed readonly system roots are `/System/Library`, `/System/Cryptexes`, `/System/Volumes/Preboot/Cryptexes`, `/usr/bin`, `/usr/lib`, `/usr/libexec`, `/usr/share`, `/bin`, `/sbin`, `/Library/Apple/System/Library`. These provide OS executables, dynamic loader/frameworks and nonsecret system resources. The literal root directory is readable because dyld requires it; this exposes root dirent names, not arbitrary subtree data. File metadata is readable for path traversal/loader operation; this policy does not promise to hide file existence/size. `/dev/null`, `/dev/random`, `/dev/urandom` have narrow device access; `/dev/null` is writable.

The running Node executable and exact non-system dylibs are discovered through the fixed `/usr/bin/otool -L` interface, recursively bounded to 96 distinct path entries. Both library aliases and canonical files are explicit readonly literals. No model-controlled PATH/read-root/loader setting is accepted; mutable workspace-hosted Node is rejected. This supports Node plus OS shell/core utilities, not all installed language toolchains. Xcode-backed `/usr/bin/python3`, globally installed npm scripts or runtimes requiring additional files may fail closed; adding toolchains is separate work. Arbitrary Homebrew/Conda/user runtime directories are not automatically exposed. The final identity lists exact roots and runtime files for review.

Only explicit nonsecret CPU/memory/page-size and kernel-version/file-limit sysctls are allowed. `kern.procargs` and arbitrary process access are not granted. Signals and process information are limited to the same sandbox. Resource quotas for CPU, memory, disk and PID count are **not** provided by this mode; retained Docker has a different resource contract.

Parent environment variables are not inherited. Shell receives a newly constructed PATH (current Node binary directory and OS tool directories), HOME/TMPDIR in the owned temporary subtree, C locale, and `OPENSSL_CONF=/dev/null` to avoid loading a Homebrew/global OpenSSL configuration. Provider credentials, proxy variables, NODE_OPTIONS, loader variables, BASH_ENV, exported shell functions and arbitrary parent variables are absent. Standard input is a fresh closed pipe, output/error fresh capture pipes; other parent descriptors are not passed. This is a specified environment set, not exhaustive detection of all possible secrets inside source files.

Within the workspace, case-insensitive ASCII `.git`, `.ssh`, `.pan-agent`, `.npmrc`, `.env` and `.env.*`, PEM/key suffixes, id_rsa/id_ed25519 names, and configured protected roots are denied for Shell and host file tools. The initial native slice also protects `.env.example`/sample/template (stricter than ordinary host behavior). Configured protected aliases are rejected; authority expansion is unavailable until #175. Symlinks cannot grant outside content; file tools reject link targets. Pre-existing regular-file hardlinks reject setup (bounded 50,000-entry no-follow scan), and creating hardlinks is denied by the OS profile. Existing host file identity checks retain their documented pathname race limitations; this is not an atomic filesystem transaction or defense against concurrent hostile host-user mutation.

## Availability and lifecycle

At task admission, the actual profile must execute a fixed computation under sandbox-exec before any model/tool invocation. Unsupported OS, missing binaries, unresolvable runtime dependencies, unsafe workspace, rejected profile or invalid setup fails before task effects; it never executes the requested command on the host. Native file tools also remain unavailable before successful start. Linux only checks unsupported behavior; it supplies no macOS enforcement evidence.

The existing command cancellation mechanism signals the process group, escalates and waits for direct-child close. Native commands additionally signal their remaining ordinary group on settlement. Controlled cancellation probes retain a delayed descendant marker and verify no late effect. This does not claim universal termination of hostile detached/reparented processes, resume after crash, or recovery of arbitrary side effects. Descendants retain OS resource restrictions even if they fork. Existing Session count limits, archives, goal/scheduler and Docker behavior are unchanged.

## Backend decision and evidence

The implementation uses a bounded repository-owned Seatbelt profile. Anthropic's [sandbox-runtime](https://github.com/anthropics/sandbox-runtime) is Apache-2.0 research-preview software, with useful filesystem/network primitives; its broader read-deny/proxy machinery and dependencies were unnecessary for this offline deny-default slice. Its source was consulted for mechanisms (including dyld root-directory access and explicit sysctls), without vendoring or adding it as a dependency. Apple sandbox-exec is deprecated and profile language is not a stable public cross-version API. Platform support is determined by actual setup/probes; no broad macOS-version certification is claimed. See [Chromium's Seatbelt overview](https://chromium.googlesource.com/chromium/src/+/HEAD/sandbox/mac/README.md).

[Builder evidence](../evidence/native172/README.md) preserves actual failures and repairs. Run focused source tests with `node --experimental-strip-types --test typescript/test/native-macos.test.ts`; on macOS these execute the real OS boundary, and on other OSes they test explicit refusal. For a clean built/installed package, run `node scripts/runtime-ci/native-macos.mjs INSTALLED_PACKAGE NEW_EXTERNAL_OUTPUT`. That command exercises actual installed CLI, TUI input/approval, Session, live file edit and sandbox Shell, substituting only deterministic model responses. The source executable control uses an ad-hoc signature on a task-owned copy of `/bin/echo` (no signing identity or private key); an unsandboxed positive control verifies that macOS code-signing rejection is not mistaken for sandbox enforcement. Raw evidence and SHA-bound independent Verdict determine acceptance.
